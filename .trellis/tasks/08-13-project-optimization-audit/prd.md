# 项目优化评估与路线规划

## Goal

基于当前代码、测试、运行模型和历史问题，判断项目是否需要重构，并形成按用户风险、变更安全性和实施成本排序的渐进式路线。目标是降低成果丢失、跨工具状态漂移和高频修改回归，不以缩短文件或更换技术栈本身作为成功标准。

## Background

- 产品已覆盖上传、转写、文字剪辑、艺术字、画中画、统一预览、最终生成和历史复用，现状可运行，不适合推倒重写。
- 2026-08-18 完整基线为 `178 passed, 1 warning in 8.18s`；所有 `web/*.js` 同时通过 `node --check`。
- 最近已成功完成测试文件、Pydantic 请求模型和历史仓库三项行为保持型拆分；`server/schemas.py` 和 `server/history_repository.py` 已建立独立边界，证明渐进式重构路径可行。
- `server/app.py` 仍有 11,734 个物理行、60 个 API 路由和 261 个顶层函数；其中 79 个函数跨度超过 50 行、25 个超过 100 行、5 个超过 200 行。该文件同时拥有路由、任务状态、AI、时间轴、FFmpeg、资源库和设置职责。
- 前端热点仍集中在 `styles.css` 13,497 行、`art-text.js` 6,015 行、`app.js` 4,952 行、`picture-in-picture.js` 2,390 行和 `editor-suite.js` 1,911 行。
- `app.js`、`art-text.js`、`picture-in-picture.js` 和 `editor-suite.js` 各自创建 `EditorTimeline` store；顶层与 iframe 之间还存在 19 类 `editor-suite:*` 消息，并传递 `timelineHtml`、`overlayHtml` 和私有 `generationPayload`。
- `JOBS`、`JOB_FILES` 仍是编辑任务权威状态。应用启动只执行存储清理，不恢复任务；磁盘上的 `cut-draft.json` 也必须先命中内存 job 才能通过 API 读取。
- 当前 `data/jobs` 约 3.09 GB，`data/history` 约 0.239 GB；临时工程状态、最终成品和资源生命周期需要更明确的边界。
- 前端测试包含静态资源契约和 5 组 Node 行为脚本，但未发现 Playwright、Selenium 或其他真实浏览器工作流测试。高风险状态迁移前缺少刷新、iframe 切换和统一生成的自动化保护。
- 本任务只做评估与规划，不直接修改业务代码。

## Requirements

- R1：梳理上传、转写、文字剪辑、艺术字、画中画、预览和最终生成的数据流，明确每一阶段的权威状态及重复副本。
- R2：区分“必须处理的行为风险”“修改时顺带提取的结构债务”和“仅影响观感的大文件”，避免以行数驱动重构。
- R3：覆盖后端职责、持久化、任务状态、媒体处理、前端状态、iframe 消息、资源生命周期和错误恢复。
- R4：结合现有测试与历史缺陷，标记自动化保护充分和不足的路径；真实浏览器行为基线必须先于高风险状态迁移。
- R5：每个 P0/P1 优化项必须包含代码或测试证据、用户影响、推荐边界、风险、预计工作量、验收方式和回滚点。
- R6：路线按 P0/P1/P2 分级，并拆成可独立验证的子任务；禁止在一个分支内完成全项目重构。
- R7：不把新功能、框架迁移、微服务化、数据库引入或纯视觉改版混入可靠性路线。
- R8：优先降低成果丢失、刷新/重启后状态回退、预览与导出不一致以及跨工具状态覆盖四类风险。
- R9：文件拆分必须保持行为，且只在对应领域有测试保护时进行；不得同时改结构、API 契约和用户行为。

## Acceptance Criteria

- [x] 给出当前系统的关键数据流与状态所有权说明。
- [x] 覆盖可靠性、编辑体验、性能、可维护性和测试五个维度。
- [x] 所有 P0/P1 建议均能追溯到当前代码、测试、运行模型或历史缺陷。
- [x] 给出可独立验收的分阶段顺序、依赖关系和回滚点。
- [x] 明确结论为“需要渐进式重构，不需要整体重写”，并列出暂不应重构的部分。
- [ ] 用户确认最终优先级后，才为第一阶段创建或启动实施子任务。

## Out of Scope

- 本轮不修改业务代码、不启动父任务实施。
- 不清理、重置、提交或覆盖当前工作区已有改动和用户媒体。
- 不更换原生 JavaScript/FastAPI 技术栈，不拆微服务，不先引入数据库或分布式队列。
- 不以拆分 `styles.css` 或追求任意文件行数阈值作为第一阶段目标。
- 不新增尚未验证用户价值的编辑功能。

## Open Question

- 是否采用推荐的“可靠性优先”顺序：先建立真实浏览器行为基线，再做可恢复项目状态、结构化前端状态和按领域拆分；代价是 `app.py`、`styles.css` 等大文件会在前几个阶段继续保持较大。若选择“整洁优先”，文件会更快变小，但无法先降低用户成果丢失和跨 iframe 回归风险。
